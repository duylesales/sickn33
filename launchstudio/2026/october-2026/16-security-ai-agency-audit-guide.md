# The Agency Guide to Auditing Security AI

Digital agencies are facing a new kind of client request. A founder walks into your office, drops a GitHub link on the table, and says, "I built this prototype with AI over the weekend. Can you guys finish it and launch it by Friday?"

Five years ago, agencies would reject this outright, insisting on a €30,000 discovery and rebuild phase. Today, rejecting AI prototypes means losing business to competitors who are willing to adapt.

However, accepting an AI-generated codebase without a rigorous security audit is a massive liability. AI tools optimize for visual completion, not for data protection — independent audits put the rate of AI-generated code containing at least one exploitable vulnerability at 45%. If you launch a client's AI app and it suffers a data breach, the legal and reputational fallout lands squarely on your agency, not on the AI vendor whose terms of service almost certainly disclaim responsibility for what their tool generated. Here is the exact framework to audit the security of AI-generated code before you agree to launch it.

## The Agency Security Audit Checklist

When your team inherits a codebase generated by Lovable, Bolt, or Cursor, you must assume the backend is compromised by default. Check these areas immediately.

### 1. Database Privilege Escalation (The BaaS Trap)

AI generators love Backend-as-a-Service (BaaS) platforms like Supabase or Firebase because they are easy to prompt. However, AI frequently uses the generic `anon` key to execute complex queries directly from the client.

- **The Audit:** Search the frontend repository for `supabase.from()` or equivalent queries. Are they bypassing Row Level Security (RLS)? Check whether RLS is even enabled on every table — Supabase allows tables to exist with RLS switched off entirely, which is the default state when a table is created through the AI's generated migration scripts.
- **The Risk:** If RLS is not strictly defined in the database, any user can manipulate the client-side JavaScript to read or delete tables belonging to other tenants. For a multi-tenant B2B client, this is the difference between a minor bug and a breach notification letter to every customer on the platform.

### 2. Secret Exposure in Client Bundles

LLMs do not understand the difference between a secure server environment and a public client bundle. They will happily take an API key you provided in a prompt and hardcode it into a React component.

- **The Audit:** Run a scanner like `trufflehog` or `gitleaks` against the full commit history — not just the current file state, since a key removed in a later commit is still visible in the repository's history. Manually inspect `.env.local` patterns and look specifically for Stripe secret keys, OpenAI API keys, or database service roles exposed in Next.js `NEXT_PUBLIC_` variables, which are compiled directly into the browser bundle by design.
- **The Risk:** Exposing a service role key gives malicious actors full administrative access to your client's database, bypassing all RLS policies entirely. This is the single most damaging finding an audit can turn up, because it does not just leak data — it grants write access to everything.

### 3. Missing Rate Limiting and DoS Vulnerabilities

AI models rarely prompt themselves to build defensive infrastructure. If an AI generates a password reset endpoint or an expensive AI-generation route, it will likely leave it completely unprotected.

- **The Audit:** Inspect the API routes. Is there any rate limiting middleware (e.g., Upstash Rate Limit) applied to routes that trigger expensive operations or send emails? Check password reset and login endpoints specifically — these are the two most commonly abused unprotected routes in AI-generated codebases.
- **The Risk:** A simple automated script could hit an unprotected AI-generation endpoint 10,000 times, racking up a massive OpenAI API bill for your client in minutes, or brute-force a login endpoint with no lockout mechanism.

### 4. Authentication and Authorization Confusion

A subtler audit item that many agencies miss on a first pass: AI-generated apps frequently confuse "is this user logged in" (authentication) with "is this user allowed to do this specific thing" (authorization).

- **The Audit:** Find an endpoint that modifies or deletes a resource — updating a record, canceling a subscription, deleting a file. Check whether the backend verifies that the logged-in user actually owns that specific resource, or whether it only checks that *a* valid session exists.
- **The Risk:** Without an ownership check, any logged-in user (including a free-tier signup created purely to probe the API) can potentially edit or delete data belonging to any other user, simply by changing an ID in the request.

### Documenting the Audit — Your Liability Shield

One step agencies routinely skip: writing down what you found. If a breach happens eighteen months after launch and a client asks what due diligence was performed before go-live, "we looked at it and it seemed fine" is not a defensible position. A proper audit produces a dated, itemized report — which endpoints were checked, which vulnerabilities were found, which were fixed before launch, and which were accepted as lower-priority risk with the client's sign-off. This single document is often the difference between an agency that can point to a documented process and one that is left explaining, after the fact, why nobody checked RLS on a table holding customer payment data. Treat the audit report as a deliverable in its own right, not just an internal engineering checklist.
