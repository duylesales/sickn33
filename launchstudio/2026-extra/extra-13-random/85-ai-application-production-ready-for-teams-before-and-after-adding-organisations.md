Your SaaS started with individuals: one teacher, one consultant, one freelancer, each with their own account. Then a customer asks the question that changes the product: "Can my colleagues use this too?" Turning a single-user app into one that serves teams is among the most consequential changes an AI-built SaaS makes. Done carelessly, it creates exactly the data leaks that end B2B deals. Done well, it is what makes an AI application production ready for business customers.

## Before: The Single-User Shape

In a single-user app generated by Lovable, Bolt or Cursor, almost everything hangs off `user_id`:

- Records belong to a user.
- Access rules — if they exist — say "you can see rows where `user_id` is you."
- Billing is per user.
- Settings are per user.

It is simple and, for individuals, correct.

## The Tempting Shortcut

The quickest way to add teams is to let users "share" records or to copy data between accounts. AI tools will happily generate a sharing table and a few extra conditions. It works for two colleagues. With ten, it becomes an unmanageable web of shares; with an admin who leaves the company, it becomes a security question nobody can answer.

## After: Organisations Make an AI Application Production Ready for Teams

The production approach introduces an **organisation** (or workspace) that owns the data:

- Records belong to an organisation, created by a user within it.
- **Memberships** link users to organisations with a **role**: owner, admin, member, viewer — or whatever your product needs.
- Access rules become "you can see rows where the organisation is one you belong to, and your role allows the action."
- Billing, settings and integrations move to the organisation.
- A user can belong to several organisations and switch between them.

## Migrating Existing Users Without Breaking Them

The hard part is not the new model; it is getting existing data into it:

1. Create a personal organisation for every existing user, with them as owner.
2. Move their records to that organisation, keeping the creating user.
3. Move their subscription to the organisation.
4. Update every query and access policy from `user_id` to organisation membership.
5. Test that every user still sees exactly what they saw before — and nothing more.

This should run on staging with a copy of real (anonymised) data first, and in production during a quiet period with a verified backup.

## Roles, Enforced Where It Counts

Roles must be checked on the server or in database policies, not just used to hide buttons. Typical rules:

- Only owners can delete the organisation or change billing.
- Admins can invite and remove members.
- Members can create and edit.
- Viewers can only read.

Every role needs negative tests: a viewer trying to edit, a member trying to invite, a removed user trying to access anything.

## Invitations and Offboarding

Invitations need expiry, single use and binding to the invited email. Removing a member must end their access immediately, including active sessions and any API tokens they created. Ownership transfer must be possible when the owner leaves.

## Billing Per Organisation

Plans move from per-user to per-organisation, often with seat counts. Subscription webhooks must update the organisation's plan; adding members may change the price; downgrades need rules for what happens to extra seats.

## Before and After at a Glance

| | Before (single-user) | After (organisations) |
| --- | --- | --- |
| Data owner | User | Organisation |
| Access rule | Own rows | Membership + role |
| Billing | Per user | Per organisation, seats |
| Sharing | Ad hoc | Built into membership |
| Offboarding | Delete account | Remove member, keep data |
| B2B readiness | Low | High |

## The Organisation Schema in SQL

Making an AI application production ready for teams starts with a small set of tables:

```sql
CREATE TABLE organisations (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name        text NOT NULL,
  plan        text NOT NULL DEFAULT 'free',
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE memberships (
  organisation_id uuid REFERENCES organisations(id) ON DELETE CASCADE,
  user_id         uuid REFERENCES auth.users(id) ON DELETE CASCADE,
  role            text NOT NULL CHECK (role IN ('owner','admin','member','viewer')),
  created_at      timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (organisation_id, user_id)
);

ALTER TABLE lesson_plans ADD COLUMN organisation_id uuid REFERENCES organisations(id);
```

Every business table gains an `organisation_id`. Access policies then check membership rather than ownership by a single user.

## Policies Based on Membership and Role

With Supabase or Postgres row-level security, membership-based policies look like this:

```sql
CREATE POLICY read_org_plans ON lesson_plans FOR SELECT
USING (EXISTS (
  SELECT 1 FROM memberships m
  WHERE m.organisation_id = lesson_plans.organisation_id
    AND m.user_id = auth.uid()
));

CREATE POLICY edit_org_plans ON lesson_plans FOR UPDATE
USING (EXISTS (
  SELECT 1 FROM memberships m
  WHERE m.organisation_id = lesson_plans.organisation_id
    AND m.user_id = auth.uid()
    AND m.role IN ('owner','admin','member')
));
```

Index `memberships (user_id, organisation_id)` so these checks stay fast. Write negative tests: a viewer cannot update, a user from another organisation cannot read, a removed member loses access immediately.

## The Migration, Step by Step

Moving existing single-user data into organisations without disruption:

1. **Create tables and columns** (organisations, memberships, `organisation_id` nullable).
2. **Backfill**: for each existing user, create a personal organisation with them as owner; set `organisation_id` on all their records.
3. **Verify**: counts per user before and after match; every record has an organisation.
4. **Switch policies**: deploy membership-based policies alongside application changes that pass the active organisation.
5. **Make `organisation_id` NOT NULL** once all writes set it.
6. **Remove old per-user policies and code paths** in a later release.

Run the whole sequence on staging with anonymised production data first, and schedule production during a quiet period with a verified backup.

## Invitations Done Securely

Invitations are a common weak point. A secure flow: an admin enters an email and role; the system creates an invitation with a random token (stored hashed), the organisation, role, inviter and expiry; the email contains a link; accepting requires the user to sign in or sign up with that exact email; the token is single-use; and the membership is created in the same transaction. Admins can revoke pending invitations. Log who invited whom — B2B customers will ask.

## Handling the Active Organisation

Users who belong to several organisations need an explicit context. Store the active organisation in the session or URL (for example `/org/{id}/...`), verify membership on every request, and never rely on the client to send an organisation ID without checking it. The interface shows which organisation is active and makes switching easy. Data from one organisation must never leak into another's views, exports or search results.

## Organisation Billing in Practice

Moving billing from users to organisations means: subscriptions attached to organisations; seat counts derived from memberships; rules for what happens when seats exceed the plan (block invitations, prorate charges or notify the owner); invoices addressed to the organisation with its VAT details; and access downgraded automatically when payments fail. Payment webhooks update the organisation's plan, and plan limits are checked on the server.

## Audit Logs for Team Accounts

Organisations expect accountability: who invited whom, who changed roles, who deleted records, who exported data. An audit log per organisation, visible to owners and admins, answers these questions and is often a requirement in B2B procurement. Store events append-only and include them in data exports.

## Offboarding and Ownership Transfer

When members leave, admins remove them and their access ends immediately — including active sessions and API tokens. Their created records remain with the organisation. When an owner leaves, ownership must be transferable to another admin; prevent organisations from ending up without an owner. Define what happens to an organisation's data when the subscription ends: grace period, export, then deletion.

## Search, Exports and Background Jobs Need Tenancy Too

Organisation separation is often correct in the main screens but missing elsewhere. Check every path that reads data: search indexes (each document tagged with its organisation and filtered at query time), exports and reports (scoped to the active organisation), background jobs and scheduled emails (processing per organisation, never mixing), AI features that retrieve documents (filtered by organisation before retrieval) and admin tools (clear about which organisation they act on). Most cross-organisation leaks in B2B SaaS happen in these secondary paths.

## Single Sign-On for Larger Customers

As organisations grow, their IT departments ask for SSO. Plan for it: map an identity provider connection to an organisation, provision members automatically on first login with a default role, and deprovision when the identity provider revokes access. Offering SSO on higher plans is common and justified by the extra complexity. Even before implementing it, design the membership model so SSO can be added without restructuring.

## Designing Roles You Will Not Regret

Start with few roles and clear meanings; adding roles later is easier than removing them. Document each role's permissions in a matrix and enforce it in one place — database policies or a shared authorisation function — rather than scattered checks in components. When customers ask for custom roles, consider whether a small set of permissions per feature would serve better than an explosion of named roles.

## Communicating the Change to Existing Users

When single-user accounts become organisations, tell users what changes and what does not: their data stays where it is, they now own a workspace, and they can invite colleagues. Provide a short guide for inviting team members and setting roles. A clear announcement turns an invisible technical migration into a visible new capability — often a reason for users to upgrade to a team plan.

## Testing the Migration Thoroughly

Beyond counts, test behaviour: log in as several migrated users and confirm their data looks identical; invite a colleague and check permissions; switch organisations; remove a member; export data; run scheduled jobs. Automated negative tests across organisations and roles should pass before the switch. The effort is modest compared with the damage a single cross-organisation leak would cause just as B2B customers are arriving.

## Why This Unlocks Business Customers

For many AI-built SaaS products, adding organisations is the step that turns individual subscriptions into business contracts. Schools, companies and agencies buy for groups, want central billing, expect administrators to control access and ask for audit logs. A single-user app, however good, cannot meet those expectations; an organisation model with enforced roles can. The engineering is well understood and, done carefully, invisible to existing users — who simply discover that they can now invite colleagues. That combination of low disruption and high commercial impact makes it one of the most valuable production investments a growing SaaS can make.

## First Step

Write down, in one table, which roles your first business customer will need and what each may see and do. That matrix is the specification for everything above.

## Remember

Sharing is a feature; organisations are a structure. Business customers need the structure.

### An AI-Native Founder in Action: A Teacher's Tool Becomes a School Product

Nienke Hellinga, a secondary-school teacher in Franeker, built Lesvoorbereiding in Lovable: a tool for planning lessons, linking materials to curriculum goals and generating differentiated exercises. About 1,300 teachers used it individually on a monthly subscription. Then three school groups asked for school licences, with shared lesson plans per department and central billing.

Her first attempt, a "share with colleague" feature generated by Lovable, created a problem within days: shared links gave access to the sharer's entire library, and teachers who changed schools kept access to former colleagues' materials. LaunchStudio's review recommended a proper organisation model instead.

Over thirteen business days, LaunchStudio's engineers introduced schools as organisations with departments, memberships and four roles; migrated all 1,300 existing users into personal workspaces without changing what they saw; rewrote access policies around membership and role with negative tests for each; built expiring, email-bound invitations and immediate removal; moved billing to organisations with seat-based school licences through Stripe; and added a workspace switcher for teachers working at more than one school. The migration ran on staging with anonymised data before going live on a Sunday evening.

**Result:** All three school groups signed licences, covering around 900 teachers, and no individual user lost access to their own materials during migration. School licences now account for most of Lesvoorbereiding's revenue.

## Frequently Asked Questions

### How do I add team accounts to a single-user AI-built SaaS?

Introduce organisations that own data, memberships with roles, and access rules based on membership — then migrate existing users into personal organisations and test that nothing changes for them.

### Is a sharing feature enough for B2B customers?

Rarely. Ad hoc sharing becomes unmanageable and hard to audit. Organisations with roles and offboarding are what business customers expect.

### How risky is migrating existing users to an organisation model?

Manageable with a tested migration on staging, a verified backup and checks that every user sees exactly what they saw before.

### How does Manifera approach multi-tenant SaaS design?

With organisation-owned data, membership-based access enforced in the database and negative tests for every role — patterns used across Manifera's B2B projects.
