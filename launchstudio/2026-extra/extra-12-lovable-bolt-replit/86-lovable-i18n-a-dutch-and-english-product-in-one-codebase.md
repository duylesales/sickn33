A Dutch product sold to Dutch customers starts in Dutch, and for a while that is the whole story. Then a customer hires an international team, a Belgian prospect asks for English, or an expat-run company wants to try it, and the founder asks the building tool to "add English".

What usually comes back is one of three things: a second copy of every screen, English strings pasted next to Dutch ones with a condition around each, or a translations table in the database that every component queries. Each works in a demonstration. Six months later every change has to be made twice, the languages have drifted apart, and nobody is sure which version is correct.

Internationalisation - i18n, for the eighteen letters between the i and the n - is not difficult. It is a structural decision with a handful of rules, and it is cheap at twenty screens and expensive at eighty. This article covers the whole of it: the architecture, where the language comes from, the formatting that is not about words, the text your server produces, the workflow for translations, and the checks that keep two languages in step.

## Three Ways It Goes Wrong

It is worth naming the patterns that AI tools produce when asked to add a language, because each looks reasonable and each fails in a characteristic way.

**Duplicated screens.** An `InvoiceList` and an `InvoiceListEn`. Every bug fixed in one must be fixed in the other, and within weeks they differ in behaviour, not only in words. This is the most expensive pattern, because it duplicates logic as well as text.

**Inline conditions.** `{lang === 'nl' ? 'Opslaan' : 'Save'}` scattered through every component. Behaviour stays shared, but the text for each language is spread across hundreds of places, nobody can review a language as a whole, and a third language means editing every condition.

**Translations in the database.** A `translations` table queried at runtime. It feels flexible and produces a slow interface, a network request for every label, an empty screen when the query fails, and translations that are invisible in code review and absent from version control.

The working approach is none of these, and it has been the standard in software for decades.

## The Architecture: Keys, Message Files, One Library

The interface refers to a key. The words live in one file per language. A library connects the two.

```json
// locales/nl/invoices.json
{
  "list": {
    "title": "Facturen",
    "empty": "Er zijn nog geen facturen.",
    "count": "{count, plural, one {# factuur} other {# facturen}}"
  },
  "actions": { "send": "Versturen", "markPaid": "Markeren als betaald" }
}
```

```json
// locales/en/invoices.json
{
  "list": {
    "title": "Invoices",
    "empty": "There are no invoices yet.",
    "count": "{count, plural, one {# invoice} other {# invoices}}"
  },
  "actions": { "send": "Send", "markPaid": "Mark as paid" }
}
```

```tsx
const { t } = useTranslation('invoices');
<h1>{t('list.title')}</h1>
<p>{t('list.count', { count: invoices.length })}</p>
```

For a React application generated by Lovable or Bolt, the two mature choices are i18next with react-i18next, and FormatJS with react-intl. Both support the ICU message format shown above - the syntax that handles plurals, variables and selections inside a translation rather than in code. Either is fine; pick one and record the choice in the conventions file so the next AI session does not introduce the other.

Three structural decisions make the files manageable as the product grows.

**Namespaces per area.** One file per part of the product - `invoices`, `clients`, `settings`, `common` - rather than one enormous file. Translators work area by area, merge conflicts become rare, and the library can load only the namespaces a screen needs.

**Keys that describe location, not content.** `invoices.list.empty`, not `noInvoicesText`. A key named after its content becomes wrong the moment the content changes; a key named after its place stays correct and tells the translator where the text appears.

**A `common` namespace for genuinely shared words** - save, cancel, delete, the days of the week - and nothing else. A `common` file that grows to hold half the product defeats the purpose of namespaces.

## Never Build Sentences From Fragments

The single most common defect in translated products, and the one AI-generated code produces most reliably:

```tsx
// Wrong: the sentence is assembled in code
{t('youHave')} {count} {t('openInvoices')}
```

Word order differs between languages, so a sentence assembled from pieces cannot be translated correctly. Dutch and English happen to align in this example; in the next sentence they will not, and a third language will break it entirely.

The rule: one key per complete sentence, with variables inside it.

```json
"openSummary": "U heeft {count, plural, one {# openstaande factuur} other {# openstaande facturen}} met een totaal van {total}."
```

The same applies to sentences containing links or emphasis. Splitting "Read our *terms* before continuing" into three keys around the link produces fragments a translator cannot order. Both main libraries support rich-text placeholders - `"Lees onze <link>voorwaarden</link> voordat u verdergaat"` - so the sentence stays whole and the component supplies the link.

## Where the Language Comes From

A product needs one clear rule for which language a person sees, applied the same way in the browser and on the server. The order that works for a B2B product:

1. **The user's saved preference**, if they are signed in and have chosen one.
2. **The language in the URL**, for public pages such as `/nl/` and `/en/`.
3. **A cookie** set when an anonymous visitor switches language.
4. **The browser's `Accept-Language` header**, as a first guess for new visitors.
5. **Dutch**, as the default.

The saved preference belongs in the database, on the user rather than the organisation:

```sql
alter table profiles
  add column locale text not null default 'nl'
  check (locale in ('nl', 'en'));
```

Storing it per user matters because the reason most Dutch products add English is that Dutch organisations employ people who prefer it. A preference stored per organisation forces the whole company into one language and produces exactly the complaint that triggered the work.

Storing it in the database rather than only in the browser matters because the server needs it: emails, PDFs, scheduled notifications and anything else produced when the user is not looking at a screen.

## Formatting Is Not Translation

Text is the visible part. Four other things differ between Dutch and English users, and getting them wrong makes a translated product feel foreign in both languages.

| | Dutch (`nl-NL`) | British English (`en-GB`) | American English (`en-US`) |
|---|---|---|---|
| Amount | € 1.250,50 | €1,250.50 | €1,250.50 |
| Date, short | 03-04-2028 | 03/04/2028 | 4/3/2028 |
| Date, long | 3 april 2028 | 3 April 2028 | April 3, 2028 |
| Time | 14:30 | 14:30 | 2:30 PM |
| First day of week | Monday | Monday | Sunday |

Two conclusions follow. First, never format numbers, money or dates by hand; use the platform's `Intl` formatters with the user's locale:

```ts
new Intl.NumberFormat(locale, { style: 'currency', currency: 'EUR' }).format(1250.5);
new Intl.DateTimeFormat(locale, { dateStyle: 'long', timeZone: 'Europe/Amsterdam' }).format(date);
```

Second, for a European product, English almost always means `en-GB` rather than `en-US`. Your English-speaking users are in Europe, work Monday to Friday with weeks starting on Monday, use the 24-hour clock at work and read day-month dates. Defaulting to American conventions is one of the clearest signals that a product was translated rather than built for its users.

Note the time zone in the example. A date formatted without one is formatted in the time zone of whatever machine runs the code - the user's laptop, or a server in another region - and the time zone article in this series describes what that does to appointment times. Locale decides how a date looks; time zone decides which date it is. Both must be explicit.

For anything where a misread date has consequences - appointments, deadlines, due dates - prefer the long format with the month written out. "3 April 2028" cannot be misread; "03/04/2028" will be, by somebody.

## Plurals, Address and Tone

**Plurals** are handled by the ICU syntax rather than by appending an "s". Dutch and English both have two forms, which hides the problem until a language with more forms is added - another reason to use the library's plural rules from the start.

**Formal and informal address** is a Dutch decision without an English equivalent. The product must choose between "u" and "je" once, write it down, and apply it everywhere, as the design system article in this series argues. For B2B products in regulated sectors - healthcare, finance, government - "u" is the safe default; for products aimed at younger or creative audiences "je" is common. The mistake is not either choice; it is mixing them, which is what machine translation from English produces because English gives it nothing to go on.

**Tone** deserves a short written guide for both languages: how error messages are phrased, whether the product addresses users directly, how formal confirmations are. Half a page, and it is what lets a translator - human or model - make consistent decisions about sentences nobody anticipated.

## Text the Server Produces

The interface is the easy half. The harder half is text generated outside the browser, and it is where AI-built products most often have Dutch hard-coded deep in the backend.

**Validation and error messages.** An edge function that returns `"Het e-mailadres is ongeldig"` has made the server responsible for language. The better contract is a code: the server returns `{ "error": "email_invalid" }` and the interface translates `errors.email_invalid`. The server stays language-neutral, and the same API serves any client.

**Statuses and categories stored in the database.** Store codes - `paid`, `overdue`, `draft` - never display text. A `status` column containing "Betaald" makes every report, filter and integration depend on Dutch, and adding English means a data migration. Translate the code at display time: `t('invoice.status.paid')`.

**Emails and notifications.** Rendered on the server with the recipient's stored locale. Templates live alongside the interface translations - or in the same message files - so a wording change does not need to be made in two systems.

**PDFs and documents.** Rendered with an explicit locale, which for invoices may deliberately differ from the user's interface language, as discussed below.

**Scheduled jobs.** A reminder sent at night has no browser and no request. It must read the locale from the recipient's profile, and the job is where hard-coded Dutch survives longest because nobody sees it during testing.

## Decide What Gets Translated

Not everything needs two languages, and the decisions should be written down rather than made screen by screen.

| Content | Translate? | Rule |
|---|---|---|
| Interface | Yes | Follows the user's locale |
| Transactional emails | Yes | Follows the recipient's stored locale |
| Invoices | Deliberately | Usually the customer's business language, not the user's interface language |
| Contracts, terms, privacy policy | Yes, with care | The Dutch version is often legally leading; say so in the English version |
| Customers' own data | No | Stays in the language it was written in |
| Marketing pages | Yes, separately | Own URLs per language, with hreflang |
| Help and documentation | Gradually | Start with the pages support links to most |

The invoice row deserves a note. A Dutch company's English-speaking office manager may use the interface in English, while the company's accountant expects invoices in Dutch. Make the invoice language a setting on the customer's organisation, not a consequence of who clicked the button.

The marketing row matters for search. A language switcher that swaps the text on a single URL is invisible to search engines in the second language. Each language needs its own URL - `/nl/prijzen` and `/en/pricing` - with `hreflang` tags pointing at each other, as the SEO articles in this series describe in detail.

## The Translation Workflow

The temptation is to have the model translate everything and ship it. For a first draft that is reasonable; as the final version of anything a customer reads, it is not.

Machine translation of interface text fails in predictable ways. Short strings lack context - "Post" as a noun or a verb, "Open" as a state or an action. Terms drift - the same Dutch concept becomes three English words across three sessions. Register mixes, as described above. And length is ignored, so a translation that fits the meaning breaks the layout.

The workflow that works:

1. **Fix a glossary first.** The twenty to forty terms your product is built on - client, practice, appointment, invoice, location - with the one agreed translation of each. This is the most valuable document in the process.
2. **Write in the language you think in.** For most Dutch founders that is Dutch; the Dutch file is the source.
3. **Draft the other language with a model, given context.** Provide the glossary, the tone guide, the key name and, where useful, a description of where the text appears. Context-free translation is where most errors come from.
4. **Have a native speaker review.** An afternoon for a product of moderate size. They catch the register problems and the terms that are correct but unidiomatic.
5. **Keep the files in the repository.** For two languages and a small team, JSON files reviewed in pull requests are enough. A translation management platform starts to pay for itself with three or more languages or external translators.

## Layout and Text Expansion

Dutch text runs noticeably longer than English for the same meaning - compound words such as "factuurinstellingen" and "betalingsherinnering" are long and cannot break where English can. A button designed around "Save" may not fit "Opslaan en versturen".

Three precautions. Design components to wrap or grow rather than truncate, particularly buttons, table headers and navigation. Use CSS `hyphens: auto` with the correct `lang` attribute on the page so long Dutch compounds can break. And test with **pseudo-localisation**: a fake locale that lengthens every string by forty percent and wraps it in markers - `[!! Ïñvöîçéš !!]` - so you can see in minutes which screens break and which strings were never extracted at all.

## Checks That Keep Two Languages in Step

Translation files drift. A feature is added in Dutch, the English keys are forgotten, and an English user sees `invoices.export.button` on their screen. Four checks prevent it.

**Key parity in CI.** A short script that loads both locales and fails the build when one has keys the other lacks:

```ts
const missing = flattenKeys(nl).filter(k => !flattenKeys(en).includes(k));
if (missing.length) { console.error('Missing in en:', missing); process.exit(1); }
```

**Unused keys.** The same script, reversed against the source code, lists keys no component uses. Not a build failure - a monthly cleanup.

**Visible gaps in development.** Configure the library to render missing keys conspicuously during development, so a gap is obvious while building rather than in production.

**A sensible fallback in production.** If a key is missing in English, show the Dutch text rather than the raw key. A gap that slips through becomes an inconvenience rather than a broken screen.

Add one line to the conventions file: every new string is added to both locale files in the same change. Assistants read it, and most of the drift stops at the source.

## Retrofitting an Existing Product

For a product that already has eighty screens of hard-coded Dutch, the work divides into a mechanical part and a judgement part.

The mechanical part - find every string, replace it with a key, add the key to the Dutch file - is exactly the kind of large, uniform change an AI agent does well, as the agent article in this series notes. Do it namespace by namespace, one area per change, reviewing a sample of each.

The judgement part is everything extraction reveals: sentences built from fragments, dates formatted by hand, amounts concatenated with "€", statuses stored as Dutch text, error messages generated on the server, emails with hard-coded templates. Each needs individual attention, and together they are most of the effort.

A realistic estimate for a product of moderate size is two to four days, with roughly a third on extraction and two thirds on the details.

## Setting This Up

For a Lovable or Bolt product adding a second language, this is typically two to four days: one i18n library adopted and recorded in the conventions file, every interface string extracted into namespaced message files with location-based keys, fragmented sentences rewritten as whole messages with ICU placeholders, a locale stored per user and resolved in a fixed order on both client and server, numbers, money and dates formatted through `Intl` with an explicit time zone and `en-GB` as the English default, server errors returned as codes and statuses stored as codes, emails, PDFs and scheduled jobs rendered with the recipient's locale, a written rule for invoice and legal document language, a glossary and tone guide in both languages, a native-speaker review of the drafted translations, pseudo-localisation to test layouts, and a CI check for key parity.

## Real example

### Two Codebases in One Folder

Thijs Wolterink built Kinderopvangplanner in Lovable: rostering and parent communication for childcare organisations, used by 21 locations with around 1,600 children.

When two locations in Amsterdam asked for English for their expat parents, he asked the tool to add it. The result was a language toggle and, behind it, conditions on 140 pieces of text across 38 screens, each rendering Dutch or English inline.

Within four months the two languages had diverged. Nine screens added since had no English at all. Dates in the English version were formatted in the Dutch order, so a parent read the 4th of March as the 3rd of April and arrived for a settling-in session a month early. Notification emails went out in the organisation's language rather than the parent's, and the English text used three different words for "group" - group, class and unit.

Three business days: a translation library adopted and all 140 strings plus the 61 untranslated ones on the newer screens extracted into keyed Dutch and English files; eleven sentences built from fragments rewritten as whole sentences with placeholders; every date, time and amount formatted through the user's locale, with unambiguous written months on the parent-facing schedule; a language preference stored per parent and used for notification emails; a glossary of fourteen terms agreed in both languages - group, location, mentor, settling-in, among others; the English drafted by the model and reviewed by a native speaker in an afternoon; and a CI check that compares the key sets and blocks a deployment when they differ.

**Result:** the English version became complete and stayed that way; the CI check blocked four deployments in the following quarter that would have shipped untranslated screens. Three further Amsterdam locations signed within two months, two of them citing the English parent communication.

> *"One parent came a month early because we wrote the date the Dutch way on the English screen. That was the moment I stopped thinking of translation as words."*
> - **Thijs Wolterink, Founder, Kinderopvangplanner (Amstelveen)**

**Cost & Timeline:** €2,900 (translation library and string extraction across 38 screens, sentence rewrites, locale-aware dates and numbers, per-user language preference for emails, bilingual glossary, native-speaker review, CI key comparison) - completed in 3 business days.

## Frequently Asked Questions

### How do I add English to a Lovable app?

Adopt one translation library, replace every piece of interface text with a key, and keep the words in one file per language and area. Avoid duplicated screens, inline conditions and translations stored in the database.

### Should I use British or American English?

For a European product, British English (`en-GB`): day-month dates, the 24-hour clock and weeks starting on Monday match how your English-speaking users actually work.

### What besides text differs between Dutch and English users?

Number and currency formatting, date order, plural rules, and in Dutch the choice between formal and informal address. Format through `Intl` with the user's locale and an explicit time zone, never by hand.

### What about text generated on the server?

Return error codes rather than messages, store statuses as codes rather than Dutch words, and render emails, PDFs and scheduled notifications with the recipient's stored locale.

### How do I stop translations going missing?

A CI check that compares the key sets of each language file and fails when they differ, conspicuous missing keys during development, a Dutch fallback in production, and a convention that every new string is added to both files in the same change.
