The thing that makes Supabase fast to build with is also the thing founders most often misunderstand: your database schema is your API. Create a table and it is immediately readable from the browser, subject only to the policies you wrote — and if you wrote none, subject to nothing.

That changes how you should think about schema design. A column is not just storage; it is a field your customers can request. A table is not just a place to put things; it is an endpoint.

Views are how you take that surface back under control, and they are underused in AI-built products because the tool never suggests them.

## The Problem With Selecting Everything

Frontend code generated by AI tools typically asks for all columns, because that is the simplest thing to write.

Three consequences. Internal fields travel to the browser — cost prices, margins, risk scores, moderation flags, internal notes — where anyone can read them in the network tab regardless of what the interface displays. Payloads are larger than they need to be, which is felt on mobile connections. And your schema becomes a published contract: every column name is now visible to whoever looks, and renaming one breaks a client you no longer control.

The instinct is to fix this in the frontend by listing columns explicitly, which is worth doing. But it is a convention, not a boundary — the next screen, or the next agent session, will select everything again.

## A View Is a Named, Stable Shape

A view is a stored query presented as if it were a table. Define one that exposes exactly the columns a screen needs, joined the way that screen wants them, and point the frontend at it.

Three things improve at once.

The internal columns are simply not there, so they cannot be requested. The frontend stops doing joins across three tables and asks one thing for one shape, which is faster and much easier to read. And you gain the freedom to reorganise the underlying tables without changing the client, because the view is the contract and the tables are an implementation detail.

That last point is what makes views worth the effort in an AI-built product specifically, where the schema will be restructured several times as the product matures.

## The Security Invoker Trap

Here is the part that causes real incidents, and it deserves reading twice.

By default, a view in Postgres runs with the permissions of whoever created it — you — rather than of whoever queries it. That means row-level security on the underlying tables is not applied to the caller. A view over an invoices table, created by an administrator, can return every organisation's invoices to any authenticated user, no matter how carefully the table's policies were written.

Every view that customers can query needs to be defined with security invoker, so it runs as the calling user and the underlying policies apply. Recent Postgres versions support this directly, and Supabase documents it — but a view created by an AI session, or by a founder in the SQL editor, will not have it unless someone asked.

The check takes two minutes: list your views, confirm each one exposed to clients uses security invoker, and test one by querying it as a user from a different organisation. If their rows come back, you have found the most serious bug in your application.

## Views Do Not Remove the Need for Policies

A related misconception: that putting a view in front of a table means the table no longer needs policies.

It does. The table remains exposed unless you have removed access to it, and a client can query it directly. Views shape convenience and reduce accidental exposure; row-level security is the actual boundary.

The complete arrangement, for a table holding customer data, is policies on the table, a view exposing the safe columns with security invoker, and access to the underlying table revoked from the API role so clients must use the view. The first of those is the one you cannot skip.

## When the View Should Be Materialized

An ordinary view runs its query every time it is read. For most screens that is exactly right.

For an expensive aggregation — a dashboard summarising a year of transactions, a leaderboard, a report over millions of rows — a materialized view stores the computed result and serves it instantly, refreshed on a schedule rather than on every request.

The trade is freshness. A materialized view refreshed hourly contains data up to an hour old, which is fine for a revenue summary and wrong for anything a user has just changed. Label it in the interface — "as of 14:00" — and the complaint disappears, because the objection is never staleness itself but staleness that looked like live data.

Two practical notes. Refreshing normally locks the view for readers unless you refresh it concurrently, which requires a unique index on it — worth setting up from the start. And a materialized view is a snapshot with no policies of its own, so it should be aggregate data that is safe for its audience, not a shortcut around per-row permissions.

## Views for Reporting, Tables for Writing

Views in Postgres can sometimes be written through, and it is usually a bad idea in a product like this.

The mental model that stays clear: reads go through views shaped for the screen; writes go through explicit application code or database functions that enforce the rules. When a write touches several tables or has conditions attached, a function is the right home for it, and it can be called from the client in one round trip.

This also gives you a natural place to put the checks that policies cannot express — a status transition that is only legal from certain states, a limit on how many of something an account may create — without scattering them through frontend code where they are advisory at best.

## Keep the Surface Small on Purpose

Once a quarter, list everything your API exposes and ask whether each item still needs to be there.

AI-built products accumulate tables from abandoned features, and an abandoned table with no policies is a data leak that nobody is watching because no code reads it. The same for views created during an experiment.

Deleting is the best outcome. Where that is premature, revoking client access is enough and takes seconds. The general principle is that the surface a customer can reach should be the set of things you deliberately published, and in most AI-built applications it is instead the set of things that were ever created.

## Generated Types Are Part of the Contract

Supabase can generate TypeScript types from your schema, and in an AI-built project this is more valuable than it first appears — not for elegance, but because it is the only mechanism that tells you what a schema change broke.

Rename a column with generated types in place and the compiler lists every file that referenced it. Rename one without them and you find out from a customer, because a query for a column that no longer exists returns nothing rather than failing loudly.

Two habits make this work. Regenerate the types as part of applying a migration rather than occasionally by hand, so they never describe a database that no longer exists. And commit them, so that a reviewer — or a coding agent reading the repository — can see the shape of the data without connecting to anything.

The second-order benefit is the one that compounds. An AI session with accurate types in the project writes queries against columns that exist, in the shapes they actually have. Without them it guesses from surrounding code, which is how a fourth name for the same concept gets introduced. Types are documentation the machine can read, and in a product where much of the code is machine-written, that is not a small thing.

## Setting This Up

For an existing Supabase product this is typically one day: an inventory of everything the API exposes, views defined for the shapes your screens actually need, security invoker confirmed on every client-facing view and verified by querying as a user from another organisation, row-level security kept as the real boundary with underlying table access revoked where a view replaces it, expensive aggregations moved to materialized views with concurrent refresh and a visible as-of time, writes routed through functions where rules apply, and unused tables and views removed from the surface.

## Real example

### The Dashboard That Showed Everyone's Numbers

Iris Molenaar built Vakantieverhuur in Lovable: booking and revenue administration for owners of holiday rentals on the Zeeland and Zuid-Holland coast, 210 owners with around 500 properties.

Her performance work had gone well. The owner dashboard — occupancy, revenue, average nightly rate, comparison to the previous year — had been slow, so an AI session created a view aggregating it, and the page became instant.

The view was created without security invoker. Row-level security on the bookings table was correct and always had been, and the view ran straight past it. Any logged-in owner who queried the view directly, rather than through the dashboard's filtered request, received the occupancy and revenue figures of all 500 properties — including those of the competitors they were pricing against.

An owner found it while building a spreadsheet against the API and reported it the same day.

Two business days: the aggregation view redefined with security invoker and verified by querying as three different owners; all nine views in the project audited, of which four were client-facing and three of those had the same defect; client access revoked on six underlying tables now reachable only through views; the year-comparison aggregation, genuinely expensive, converted to a materialized view refreshed every fifteen minutes with a unique index for concurrent refresh and an "updated at" line shown on the dashboard; two tables from an abandoned pricing experiment removed from the API surface entirely; and a test added that queries every client-facing view as a second-organisation user and fails if any row comes back.

**Result:** the exposure closed within a day of being reported, and the automated cross-tenant test has since caught two further views created in later AI sessions before they reached production. Dashboard load time stayed under 200 milliseconds.

## Frequently Asked Questions

### Why does a view bypass row-level security?

Because by default it runs with the creator's permissions rather than the caller's. Define client-facing views with security invoker so the underlying table policies apply to whoever is querying.

### Do views replace the need for policies?

No. The underlying table is still exposed unless you revoke access, and policies remain the actual security boundary. Views shape the surface; they do not enforce it.

### When should a view be materialized?

When the query is expensive and the data does not need to be current to the second — dashboards, summaries, reports. Show the as-of time, and set up a unique index so refreshes can run concurrently.

### Should the frontend select all columns?

No. Expose a view containing exactly what the screen needs. Selecting everything sends internal fields to the browser and turns your column names into a published contract.

### How do I know what my Supabase API exposes?

List the tables and views reachable by the API role and check each one deliberately. AI-built projects accumulate tables from abandoned features, and an unused table without policies is a leak nobody is watching.
