Mollie is the payment provider many Dutch and Belgian founders choose: Amsterdam-based, strong on iDEAL and Bancontact, and clear pricing. AI app builders, however, default to Stripe. Ask Lovable or Bolt for a Mollie integration and you will usually get something that creates a payment and redirects the customer, but not the parts that make it reliable. This guide shows the full Mollie integration, step by step, for an app with a Supabase backend.

## Key Takeaways

- **Mollie is an Amsterdam-based payment provider** strong on iDEAL, Bancontact and SEPA, and a natural fit for Dutch and Belgian businesses.
- **AI builders default to Stripe,** so Mollie integrations generated by prompts often miss the parts that make payments reliable.
- **Mollie's webhook sends only a payment ID.** Your server fetches the real status from Mollie's API, which makes forged webhooks harmless.
- **Amounts are two-decimal strings, prices come from your database,** and handlers must be idempotent because Mollie may call your webhook several times.
- **A complete Mollie integration** with statuses, refunds and testing is typically part of a €1,200-€3,500 LaunchStudio quote.

## What You Need Before Starting

- A Mollie account with a website profile approved for your domain
- Test and live API keys (they start with `test_` and `live_`)
- A Supabase project with edge functions enabled, or another server environment
- An `orders` table with at least: id, user_id, amount, currency, status, mollie_payment_id

## Step 1: Store Keys Server-Side Only

Mollie API keys are secret. Add them as edge function secrets, never in frontend code or `.env` files that end up in the browser bundle.

```bash
supabase secrets set MOLLIE_API_KEY=test_xxxxxxxxxxxxxxxx
```

Switch to the `live_` key only when you are ready to accept real payments, and never commit either key to git.

## Step 2: Create the Payment in an Edge Function

The browser asks your function to pay for an order. The function looks up the order, checks it belongs to the user, and creates the payment at Mollie.

```ts
// supabase/functions/create-payment/index.ts (simplified)
const order = await getOrderForUser(orderId, userId); // server-side lookup
const res = await fetch("https://api.mollie.com/v2/payments", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${Deno.env.get("MOLLIE_API_KEY")}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    amount: { currency: "EUR", value: order.amount.toFixed(2) },
    description: `Order ${order.id}`,
    redirectUrl: `https://yourapp.nl/orders/${order.id}`,
    webhookUrl: "https://<project>.functions.supabase.co/mollie-webhook",
    metadata: { order_id: order.id },
  }),
});
const payment = await res.json();
await savePaymentId(order.id, payment.id);
return Response.json({ checkoutUrl: payment._links.checkout.href });
```

Two details AI tools often get wrong: Mollie expects the amount as a **string with two decimals** (`"19.95"`), and the price must come from your database, not from the request.

## Step 3: Handle Mollie's Webhook the Right Way

Mollie's webhook is different from Stripe's. It does not send the payment details, only the payment ID. Your function must then **fetch the payment from Mollie's API** to read its status. That is a security feature: a forged webhook cannot claim a payment was paid, because your function asks Mollie directly.

```ts
// supabase/functions/mollie-webhook/index.ts (simplified)
const form = await req.formData();
const id = form.get("id");
const payment = await fetchMolliePayment(id); // GET /v2/payments/{id}
await updateOrderFromPayment(payment.metadata.order_id, payment.status);
return new Response("OK", { status: 200 });
```

Make `updateOrderFromPayment` **idempotent**: if the order is already paid, a second webhook changes nothing. Mollie may call your webhook several times as a payment's status changes.

## Step 4: Map Every Status

| Mollie status | What your app should do |
| --- | --- |
| `open` | Wait, show "payment pending" |
| `pending` | Wait, some methods take longer to confirm |
| `authorized` | For methods that support capture, decide when to capture |
| `paid` | Fulfil the order, grant access, send receipt |
| `canceled` | Release reserved stock or seats, allow retry |
| `expired` | Same as canceled |
| `failed` | Show a clear message, allow retry with another method |

The redirect page should read the order status from your database, not assume success because the customer returned.

## Step 5: Refunds and Chargebacks

Refunds should be initiated from an admin action that calls a server-side function. Chargebacks arrive as status changes on the original payment, so your webhook handler should be ready to revoke access when a paid order is charged back.

## Step 6: Go Live Checklist

- Website profile approved in Mollie for the live domain
- `live_` key set in production secrets, `test_` key only in staging
- Webhook URL reachable from the internet, returning 200 quickly
- One real low-value payment tested end to end on mobile
- Receipts and invoices contain your company details and BTW information

## Architecture at a Glance

A reliable Mollie integration in a Supabase-backed app has four moving parts:

| Component | Responsibility |
| --- | --- |
| `orders` table | Source of truth for what the customer owes and the order's status |
| `create-payment` edge function | Validates the order, creates the Mollie payment, stores the payment ID |
| `mollie-webhook` edge function | Fetches the payment from Mollie and updates the order idempotently |
| Return page | Reads the order status from your database and shows the right message |

Nothing in the browser decides that an order is paid. That single rule prevents most payment bugs in AI-built apps.

## Idempotency in Practice

Mollie calls your webhook whenever a payment's status changes, and it retries if your endpoint does not respond successfully. Your handler must therefore produce the same result no matter how many times it runs. In practice:

- Update the order's status only if the new status differs from the stored one
- Trigger side effects, such as sending a receipt or granting access, only on the transition into `paid`, and record that you did so
- Respond quickly with a 200 status, doing slow work afterwards or in a queue
- Log every webhook call with the payment ID and resulting status

The same principle applies to creating payments: if a customer double-clicks, your function should reuse an existing open payment for that order instead of creating a second one.

## Security Considerations

- **Keys:** Mollie test and live keys are secrets. They belong in edge function secrets, separated per environment, and must be rotated if exposed. OWASP's Secrets Management Cheat Sheet describes the practices.
- **Webhook endpoint:** because Mollie's webhook carries only an ID, you do not need to trust its payload; you always confirm by calling Mollie. Still, rate-limit the endpoint and ignore unknown IDs.
- **Metadata:** store your order ID in the payment's metadata so the webhook can find the order, but never put personal data you do not need in payment descriptions.
- **Refunds:** restrict refund actions to authorised staff through a server function, and log who issued each refund.

## Multiple Payment Methods

Mollie supports many methods beyond iDEAL, including cards, Bancontact, SEPA bank transfer and others depending on your account. You can let Mollie's hosted checkout show available methods or pre-select one based on the customer's country. For Belgian customers, enabling Bancontact is usually as important as iDEAL is for Dutch customers.

## Going Live Without Surprises

Before switching to the live key, run the full set of test outcomes, confirm the webhook URL is reachable from the internet over HTTPS, and verify that your invoices or receipts include your company details and VAT information. After launch, reconcile Mollie settlements with orders monthly. A small mismatch caught in the first month is an afternoon's work; the same mismatch caught at year-end is a week.

## Handling Orders That Never Get Paid

Not every customer who starts a payment completes it. Some close the tab, some change their mind, some get distracted by their banking app. Without a plan, these abandoned orders pile up, block stock or seats, and clutter reports. A clean approach:

- Give each pending order an expiry time that matches the payment method, for example 15-30 minutes for iDEAL
- When Mollie reports `expired` or `canceled`, release reserved stock or booking slots automatically
- Offer a "complete your payment" link in a reminder email for high-value orders, using a fresh payment for the same order
- Report abandoned orders weekly; a sudden rise often points to a checkout problem rather than customer behaviour

## Logging and Support

When a customer writes "I paid but nothing happened", you should be able to answer in minutes. Log every payment creation and every webhook call with timestamps, the Mollie payment ID, the order ID and the resulting status. Give support staff a simple screen that shows this timeline for an order. Most "missing payment" cases turn out to be expired payments, payments to a different order, or a webhook that failed because of a deployment; a timeline makes each of those obvious.

## Testing Your Webhook Locally and in Staging

Mollie needs to reach your webhook over the internet, which makes local testing awkward. Two practical options: deploy the webhook function to a staging Supabase project and point test payments there, or use a tunnelling tool during development. Either way, keep separate test and live keys per environment, and never point live payments at a staging endpoint.

## Mollie Profiles and Multiple Websites

A Mollie account can contain several website profiles, each with its own payment methods and settings. If you run a staging site and a production site, or several brands, keep them as separate profiles with separate keys. That keeps test traffic out of production reports and lets you enable methods per brand.

## Frequently Asked Questions

### Why does Mollie's webhook only send a payment ID?

It is a deliberate security design. Because your server must fetch the payment from Mollie's API to learn its status, a forged webhook cannot convince your app that a payment succeeded. It also means you always work with the latest status, even if webhooks arrive out of order.

### Can I use Mollie with Lovable and Supabase?

Yes. The cleanest setup uses Supabase edge functions: one to create payments and one to receive webhooks. The Lovable frontend calls the first function and reads order status from the database. Lovable may need explicit instructions, since it tends to default to Stripe.

### Should I store Mollie amounts as decimals or cents?

Store amounts in your database as integers in cents to avoid rounding errors, and convert to Mollie's two-decimal string format only when creating the payment. Many AI-generated integrations use floating point numbers, which can produce amounts like 19.949999.

### Why does an Amsterdam-based parent company matter for Mollie integrations?

Mollie is an Amsterdam company built for Dutch and European payment habits. Manifera's Amsterdam base and long Dutch client list mean its engineers are familiar with how Dutch customers pay, how Mollie behaves in practice and what Dutch bookkeeping needs from payment records.

### Does a reliable payment integration help search and AI visibility?

Indirectly. Clear pricing pages, stable checkouts and accurate structured data about accepted payment methods help both search engines and AI assistants recommend you to Dutch users. Broken checkouts produce poor engagement signals and negative reviews that can be cited.
