In the prototype phase, changing the database is effortless. You ask Lovable or Bolt for a new feature, it adds a column or a table, and the change appears instantly. Nobody notices if the app breaks for a few seconds, because nobody is using it.

After launch, the same habit becomes dangerous. A schema change that locks a busy table can freeze the app for every user. Renaming a column breaks the version of the frontend still running in users' browsers. A backfill that updates a million rows in one statement can slow everything down for minutes. A policy change can suddenly hide data from customers or expose it to the wrong ones.

Zero-downtime migrations are a set of habits that let you change your database while the app keeps running. This guide explains them for Supabase, in practical terms.

## Key Takeaways

- **All schema changes should be migrations:** versioned SQL files in your repository, applied through a pipeline, never ad-hoc edits in the dashboard.
- **Use the expand and contract pattern** for breaking changes: add the new structure, migrate code and data, then remove the old structure later.
- **Watch locks.** Some operations take strong locks on tables; keep them short or use alternatives that avoid long locks.
- **Build indexes and validate constraints in ways that avoid blocking writes,** and backfill data in batches.
- **Test every migration on staging with realistic data** and have a rollback or fix-forward plan.

## The Migration Workflow

Supabase supports migrations through its CLI. The basic workflow:

1. **Develop locally or against a development project.** The Supabase CLI can run a local stack.
2. **Create a migration file** describing the change in SQL, either written by hand or generated by comparing schemas.
3. **Commit the migration** to your repository alongside the code that uses it.
4. **Apply to staging** through your pipeline and test.
5. **Apply to production** through the same pipeline, at an appropriate time.

The key rule: **production is changed only by migrations.** If someone changes a table in the dashboard, or an AI builder applies changes directly to the production project, the migration history no longer matches reality, and the next migration may fail or behave unexpectedly.

For apps built with Lovable or Bolt connected directly to a production Supabase project, the first step is often to separate environments: a staging project connected to the builder, and a production project that only receives migrations. Our guide on [setting up a staging environment for a Lovable app](https://launchstudio.eu/en/blog/how-do-i-set-up-a-staging-environment-for-a-lovable-app) explains this.

## Why Migrations Cause Downtime

Postgres uses locks to keep data consistent. Some schema changes require an `ACCESS EXCLUSIVE` lock, which blocks all reads and writes on the table until the change completes. If the change is quick, users notice nothing. If it is slow, or if it has to wait for a long-running query to finish before acquiring the lock, every request touching that table queues up behind it.

Common causes of migration-related outages:

| Operation | Risk |
| --- | --- |
| Adding a column with a volatile default on a large table | May rewrite the table while locked |
| Changing a column's type | Often rewrites the table |
| Adding a `NOT NULL` constraint on an existing column | Scans the table while holding a lock |
| Creating an index normally | Blocks writes while building |
| Adding a foreign key | Validates all rows while holding locks |
| Renaming or dropping a column | Breaks code still using the old name |
| Large `UPDATE` in one statement | Long transaction, heavy load, lock contention |

The PostgreSQL documentation on explicit locking lists which commands take which locks. You do not need to memorise it, but you should check it for any change to a busy table.

## The Expand and Contract Pattern

Breaking changes, such as renaming a column, splitting a table or changing a type, should not happen in one step. Instead:

**1. Expand.** Add the new structure alongside the old one. For a rename, add the new column.

**2. Migrate.** Deploy code that writes to both old and new structures, backfill existing data into the new structure and then switch reads to the new one.

**3. Contract.** Once no code uses the old structure, and you are confident, remove it in a later migration.

Example: renaming `customer_name` to `company_name`.

| Step | Migration | Code |
| --- | --- | --- |
| 1 | Add `company_name` column, nullable | No change |
| 2 | Backfill `company_name` from `customer_name` in batches | Write to both columns |
| 3 | None | Read from `company_name` |
| 4 | Drop `customer_name` | Stop writing to old column |

Each step is safe on its own, and the app keeps working throughout. It takes longer than a direct rename, but it never breaks users.

## Safe Patterns for Common Changes

**Adding a column.** Adding a nullable column without a default is fast. In recent Postgres versions, adding a column with a constant default is also fast, because Postgres stores the default without rewriting the table. Avoid volatile defaults, such as random values, on large tables.

**Adding NOT NULL.** Add a check constraint with `NOT VALID`, which does not scan existing rows, backfill any nulls, then `VALIDATE CONSTRAINT`, which checks rows without blocking writes. Then you can set `NOT NULL` with minimal locking, or keep the validated check constraint.

**Adding a foreign key.** Similarly, add the constraint as `NOT VALID` and validate it separately.

**Creating an index.** Use `CREATE INDEX CONCURRENTLY` on busy tables, which builds the index without blocking writes. It cannot run inside a transaction block, so it may need to be applied as a separate migration step or outside the default transactional migration flow, depending on your tooling.

**Changing a column type.** Use expand and contract with a new column, rather than altering the type in place.

**Dropping a column or table.** Only after confirming no code uses it, including older frontend versions that might still be cached in users' browsers.

## Backfilling Data in Batches

Updating millions of rows in a single statement creates a long transaction, generates heavy load and can lock rows that the app needs. Instead, backfill in batches:

- Update a limited number of rows per batch, for example a few thousand, ordered by primary key.
- Commit after each batch.
- Pause briefly between batches if the database is busy.
- Track progress so the job can resume if interrupted.

Run backfills as a script or background job rather than inside a migration file, so a slow backfill does not block your deployment pipeline.

## Lock Timeouts: A Safety Net

Set a `lock_timeout` at the start of migrations that touch busy tables. If the migration cannot acquire its lock within, for example, a few seconds, it fails instead of waiting and causing every other query to queue behind it. A failed migration can simply be retried at a quieter moment; a stuck one causes an outage.

## Policies, Functions and Triggers

In Supabase, Row Level Security policies, database functions and triggers are part of your schema and should be in migrations too. Changing them carries specific risks:

- **Dropping and recreating a policy** leaves a brief window with different access rules. Within a single transaction, the change is atomic, which avoids that window.
- **Tightening a policy** can suddenly hide data that features depend on. Test with each role on staging.
- **Loosening a policy** can expose data. Review every change to policies carefully.
- **Changing a function used by policies** affects every query on those tables.

Include tests for access rules that run after migrations on staging, so policy regressions are caught before production.

## Coordinating Code and Schema Deployments

Frontend and backend code deploy separately from database migrations, and users may keep old versions of a single-page app open for hours. Plan so that:

- **The database is compatible with both the old and new code** during the transition.
- **Migrations that add things deploy before the code that uses them.**
- **Migrations that remove things deploy after the code no longer uses them.**

This ordering is what expand and contract achieves.

## Testing and Rollback

- **Test every migration on staging with production-like data volumes.** A migration that takes 50 milliseconds on 100 rows may take minutes on 10 million.
- **Back up before risky migrations,** and know how to restore. Supabase point-in-time recovery on paid plans helps.
- **Prefer fix-forward over rollback** for most issues: write a new migration that corrects the problem, rather than trying to reverse a partially applied change.
- **Keep a written plan** for high-risk migrations, including how you will know if something went wrong.

## A Pre-Flight Checklist for Every Migration

Before applying a migration to production, run through these questions. For small changes, it takes a minute; for large ones, it can prevent an outage:

1. **Has it run on staging with realistic data volumes?** Note how long it took.
2. **Which tables does it touch, and how busy are they?** Busy tables deserve extra care.
3. **Which locks will it take?** Check the PostgreSQL documentation if unsure.
4. **Is a lock timeout set?**
5. **Is it compatible with the code currently running,** including frontend versions still open in users' browsers?
6. **Does it change access policies?** If so, have the access tests passed on staging?
7. **Is there a backup or point-in-time recovery available,** and do you know how to use it?
8. **What is the fix-forward plan** if something goes wrong?
9. **Is the timing sensible?** Avoid peak hours for anything that might be slow.

Write the answers in the pull request description. It creates a record of decisions and makes reviews faster.

## Common Mistakes in AI-Built Apps

**Schema changes applied directly by the builder to production.** No history, no review.

**Destructive changes generated by AI.** An agent "simplifying" the schema by dropping and recreating a table, losing data.

**Renames in one step.** Breaking every client still using the old name.

**Indexes built without `CONCURRENTLY` on busy tables.** Writes blocked during peak hours.

**Backfills inside migrations.** Deployments that hang or time out.

**Policies edited in the dashboard.** Access rules that differ from what is in the repository.

## Frequently Asked Questions

### Can I let Lovable or Bolt change my production database directly?

It is risky once you have real users. Builder-applied changes bypass review, may lock tables or break running clients, and leave your migration history out of sync. Connect the builder to a staging project and apply changes to production only through reviewed migrations.

### How do I rename a column without downtime?

Use expand and contract: add the new column, write to both columns, backfill existing data in batches, switch reads to the new column, and remove the old column in a later migration once nothing uses it.

### Why did my migration lock the whole table?

Some operations, such as changing column types, adding certain constraints or creating indexes without `CONCURRENTLY`, take strong locks or rewrite tables. On large or busy tables, use the safer alternatives described above and set a lock timeout so migrations fail fast instead of blocking.
