For a Dutch SaaS founder, one language is rarely enough. Dutch customers expect Dutch, especially in sectors such as healthcare, local government, education and trades. At the same time, many Dutch companies employ international staff who prefer English, Belgian customers may use Dutch or French, and growth beyond the Netherlands usually starts in English. A tool that only speaks one language limits its market from the start.

AI builders make the first version fast, but they almost always hard-code text directly into components: button labels, error messages, emails and placeholder text, often in a mix of English and Dutch depending on how prompts were written. Adding a second language later means finding and extracting hundreds of strings and fixing date, number and currency formatting throughout the app.

Internationalisation, usually shortened to i18n, is the work of preparing an app for multiple languages. This guide explains how to do it well in an AI-built React app, for both the product and its search visibility.

## Key Takeaways

- **Separate text from code.** Every user-facing string goes into translation files, referenced by keys, so languages can be added without changing components.
- **Use the browser's Intl APIs** for dates, numbers and currency rather than formatting by hand, because Dutch and English conventions differ.
- **Choose a clear URL strategy** for public pages, such as `/nl/` and `/en/` paths, and add hreflang annotations for search engines.
- **Translate everything the user sees,** including emails, PDFs, error messages and notifications, not only the interface.
- **AI can draft translations; native speakers should review** key screens, legal text and marketing pages.

## What Internationalisation Involves

| Area | What needs to happen |
| --- | --- |
| Interface text | Extract strings into translation files with keys |
| Language selection | Detect, store and allow switching of the user's language |
| Formatting | Dates, times, numbers, currency and percentages per locale |
| Pluralisation | Correct forms for "1 item" and "3 items" in each language |
| URLs and SEO | Language-specific URLs, hreflang tags and translated metadata |
| Emails and documents | Templates for transactional emails, invoices and reports in each language |
| Database content | Translated names, descriptions and categories where content is shared |
| Validation and errors | Translated validation messages from frontend and backend |
| Legal text | Privacy policy and terms in each language |

## Choosing a Library

For React apps built with Vite, which most Lovable and Bolt projects use, **react-i18next** is a widely used option. For Next.js apps, often generated by v0, **next-intl** integrates well with routing and server components. Both support translation files, interpolation, pluralisation and language switching.

A minimal react-i18next setup:

```typescript
import i18n from "i18next";
import { initReactI18next } from "react-i18next";
import nl from "./locales/nl.json";
import en from "./locales/en.json";

i18n.use(initReactI18next).init({
  resources: { nl: { translation: nl }, en: { translation: en } },
  lng: "nl",
  fallbackLng: "en",
  interpolation: { escapeValue: false },
});
```

And in a component:

```tsx
const { t } = useTranslation();
return <button>{t("invoice.send")}</button>;
```

With translation files such as:

```json
{ "invoice": { "send": "Factuur versturen", "sent_count": "{{count}} factuur verstuurd", "sent_count_other": "{{count}} facturen verstuurd" } }
```

## Extracting Strings From an AI-Built App

This is usually the largest part of the work. A systematic approach:

1. **Inventory screens** and list every visible text, including placeholders, tooltips, empty states, toasts, confirmation dialogs and error messages.
2. **Define a key structure** by feature, such as `invoice.send`, `settings.profile.title`, `errors.network`.
3. **Extract strings** component by component, replacing literals with `t()` calls. AI coding tools are helpful here when given clear instructions and the key structure.
4. **Search for leftovers** using tools that flag hard-coded strings in JSX, and check the app in both languages.
5. **Add a rule to your project instructions:** all new user-facing text must use translation keys, with both Dutch and English entries.

The last step matters. Without it, the next prompt that adds a feature will hard-code text again.

## Formatting Dates, Numbers and Currency

Dutch and English conventions differ in ways that cause real bugs:

| Value | Dutch (nl-NL) | English (en-GB) |
| --- | --- | --- |
| Date | 25-05-2028 or 25 mei 2028 | 25/05/2028 or 25 May 2028 |
| Number | 1.234,56 | 1,234.56 |
| Currency | € 1.234,56 | €1,234.56 |
| Time | 14:30 | 14:30 or 2:30 pm |
| Week start | Monday | Monday in the UK, Sunday in the US |

Use `Intl.DateTimeFormat`, `Intl.NumberFormat` and related APIs with the user's locale, rather than formatting strings by hand. They use Unicode CLDR data and handle details correctly. Also pay attention to input: users typing "1.234,56" in a Dutch interface expect it to be read correctly. Our article on [money, rounding and currency bugs in SaaS](https://launchstudio.eu/en/blog/money-rounding-and-currency-bugs-in-saas) covers this in depth.

## Language Selection

A practical approach for most B2B SaaS products:

- **Default** based on the account's country or the browser's language at first visit.
- **Store the preference** on the user profile, so it follows them across devices.
- **Allow switching** in settings and on public pages.
- **Respect organisation settings** where relevant, for example a company that wants all documents in Dutch regardless of individual preferences.

Avoid automatically redirecting public pages based on IP location, which can confuse users and search engine crawlers.

## URLs and SEO for Public Pages

For marketing pages, documentation and other public content, language-specific URLs help both users and search engines:

- **Use subdirectories,** such as `example.com/nl/` and `example.com/en/`, which keep authority on one domain and are simple to manage.
- **Add hreflang annotations** linking each page to its translations, following Google's guidance on localised versions, including an `x-default` for the fallback.
- **Translate metadata:** titles, descriptions and structured data.
- **Render public pages on the server** so crawlers see translated content without running JavaScript.
- **Keep translations equivalent,** not machine-translated thin copies, because search engines and readers notice low-quality translations.

Logged-in app screens usually do not need language-specific URLs; a user preference is enough.

## Emails, PDFs and Notifications

Translating the interface but sending Dutch users English emails is a common gap. Make sure that:

- **Transactional emails** such as sign-up confirmation, password reset, invoices and notifications use the recipient's language.
- **Authentication emails** from Supabase Auth or similar providers are customised per language, which may require sending emails through your own function rather than the provider's default templates.
- **PDFs,** such as invoices and reports, use the correct language and number formats, and legally required invoice content is present in the relevant language.
- **Push and in-app notifications** are generated in the recipient's language, which means the backend needs access to translations too.

## Translated Database Content

Some content lives in the database rather than in code, such as product categories, plan names, onboarding tips or templates. Options:

- **Translation columns,** such as `name_nl` and `name_en`, simple for a fixed set of languages
- **A JSON column** with translations per language, flexible but harder to query
- **A separate translations table,** linking records, fields and languages, most flexible for many languages

For two languages, translation columns are often enough. Choose a structure that your admin interface can edit comfortably.

## Using AI for Translation

AI models produce good first drafts of Dutch and English translations, and they help with consistency when given a glossary. A sensible workflow:

1. **Create a glossary** of key product terms and their approved translations, such as "workspace" and "werkruimte".
2. **Generate drafts** with AI, including the glossary and context about where each string appears.
3. **Review** important screens, onboarding, error messages, emails and legal text with a native speaker.
4. **Check tone and formality.** Dutch business software often uses "je" in friendly products and "u" in formal contexts such as healthcare or government. Decide once and apply it consistently.

## Keeping Translations in Sync Over Time

The first translation pass is a project; keeping translations current is a habit. Without a process, new features ship with missing keys, and users see raw identifiers such as `settings.billing.title` or fall back to the wrong language. A few practices prevent that:

- **Fail the build on missing keys.** A small script can compare translation files and report keys that exist in one language but not the other. Run it in your deployment pipeline.
- **Show missing translations clearly in staging.** Configure the library to display a visible marker for missing keys in non-production environments, so testers notice them.
- **Review translations with each release.** Include new strings in the release checklist and have someone fluent check them before deploying.
- **Keep the glossary alive.** When the product introduces a new concept, add it to the glossary with approved Dutch and English terms before it appears in the interface.
- **Remove unused keys periodically.** Translation files grow with every feature; unused keys confuse translators and AI tools alike.
- **Track language usage.** Product analytics can show which languages users choose, which helps decide where to invest translation effort.

These habits take minutes per release and prevent the gradual decay that makes multilingual apps feel unfinished.

## Common Mistakes

**Concatenating strings.** Building sentences like `"Je hebt " + count + " berichten"` breaks grammar in other languages. Use interpolation and plural rules.

**Hard-coded formats.** Dates formatted as `MM/DD/YYYY` confuse Dutch users.

**Untranslated backend messages.** Validation errors from the server appear in English inside a Dutch interface.

**Forgetting authentication emails.** Users receive a Dutch interface but English password reset emails.

**Machine translation without review on public pages.** Damages credibility and search performance.

**Layout breaks.** Dutch words are often longer than English ones, so buttons and labels overflow. Test layouts in both languages.

## Frequently Asked Questions

### When should I add multiple languages to my SaaS?

Ideally before your codebase grows large, because extracting strings later takes more effort. If you already serve Dutch and international users, or plan to expand within a year, setting up i18n during your production launch is usually cheaper than retrofitting it later.

### Can AI tools translate my app automatically?

AI produces good first drafts, especially with a glossary and context for each string. Review key screens, onboarding, emails, error messages and legal text with a native speaker, and decide on tone and formality, such as "je" or "u" in Dutch, before translating.

### How do I make translated pages rank in Google?

Use language-specific URLs such as `/nl/` and `/en/`, add hreflang annotations linking translations, translate titles and descriptions, render public pages on the server and make sure translations are complete and of good quality rather than thin machine translations.

### How does Manifera's experience help with multilingual products?

Manifera works across the Netherlands, Singapore and Vietnam and has built multilingual systems for clients for 11+ years. LaunchStudio applies that experience to structure translations, formatting and content so new languages can be added without rework.

### Does multilingual content help AI search visibility?

Yes. AI answer engines respond to questions in many languages and draw on content in the language of the question. High-quality Dutch and English pages make it more likely your product is found and cited by Dutch and international users alike.
