"It depends" sounds like a dodge when a CFO asks for a web app development cost estimate, but it's the only honest answer available before a specific scoping exercise happens — and a vendor willing to give a firm number without that exercise is telling a CFO more about their sales process than about the actual project.

**The Pain:** A CFO needs a web app development cost figure to build a budget, and every vendor conversation either produces a suspiciously precise number delivered before any real scoping has happened, or an unhelpfully vague range that doesn't actually support building a real budget — neither of which is the genuinely useful thing a CFO actually needs, which is a specific number tied to a specific, agreed scope.

**The Agitation:** A CFO who accepts a precise-sounding number given before real scoping, because it feels more useful than "it depends," typically discovers that number was never actually grounded in the project's real requirements — it was a sales anchor, and the real cost, once scoping happens properly, diverges from it substantially, forcing a budget conversation that's more painful than if the CFO had simply waited for an honest, scoped number in the first place.

## Getting to a Real Number, Not a Sales Anchor

A genuinely useful web app development cost figure requires a scoping process that happens before the number is quoted, not after, and a CFO who understands what that process should look like can tell the difference between a real estimate and a sales anchor.

The first step of real scoping is a detailed requirements conversation covering not just the feature list but the underlying complexity of each feature — whether "user dashboard" means a simple data display or a complex, real-time, customizable interface, because those two things share a name and differ enormously in cost. A vendor who quotes a number without this conversation is quoting against an assumption, not the actual project.

The second step is technical discovery specific to any existing systems the new web app needs to integrate with or replace — reviewing what's actually there, not just taking a verbal description at face value, because existing systems frequently have undocumented complexity that only becomes visible on direct inspection, and a cost estimate built without that inspection is built on an incomplete picture.

The third step is an explicit conversation about non-functional requirements — expected user load, performance expectations, security and compliance needs — because these requirements can dramatically change the underlying architecture and cost even when the visible feature list stays identical, and they're the requirements most likely to be assumed rather than explicitly discussed before a number is quoted.

The fourth step, and the one that converts a scoping exercise into an actually useful budget number, is presenting the estimate with its underlying assumptions explicit and visible — not just a total figure, but what specifically that figure assumes about scope, complexity, and requirements, so that if reality diverges from those assumptions during development, the CFO can see exactly which assumption changed and why the cost moved, rather than experiencing an unexplained overrun.

A CFO who insists on this scoping process before accepting any web app development cost number gets something genuinely useful to plan against. A CFO who accepts a fast, precise-sounding number without it gets a sales anchor that will very likely need renegotiating once the real scope becomes clear.
